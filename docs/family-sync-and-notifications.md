# Мур-календарь — семейная синхронизация и уведомления

Краткий продуктово-технический план (v1 → v2). Контекст: сейчас HTML-стаб + debug APK на WebView с данными только в `localStorage` (`mur-calendar-times`, `mur-calendar-theme`), без облака и пушей.

---

## 1. Семейный аккаунт и синхронизация

### Цель
Одна «семья / household»: мама отмечает кормление у себя — папа и остальные сразу видят то же в календаре.

### Модель (практично для v1)
| Сущность | Смысл |
|----------|--------|
| **User** | Личный аккаунт (email / телефон / Google) |
| **Household** | Общая «квартира» с котами и календарём кормлений |
| **Member** | User ↔ Household, роль `owner` или `member` |
| **Invite** | Короткий код (6–8 символов) или deep-link, TTL 24–72 ч, одноразовый/многоразовый с лимитом |

**Роли v1:** `owner` (создаёт семью, приглашает, может удалить участника) и `member` (читает/пишет кормления). Отдельный «только просмотр» — опционально в v2.

**Данные кормления (эволюция модели):** сейчас слот = строка времени `HH:MM`. Для семьи расширить запись:

```
{ time, fedByUserId, fedByName, createdAt, updatedAt, clientId }
```

`clientId` (UUID с устройства) нужен для идемпотентности и офлайн-слияния.

### Бэкенд: выбор стека

**Рекомендация v1 → v2: Supabase** (Auth + Postgres + Realtime + RLS).

| Вариант | Плюсы | Минусы | Вердикт |
|---------|--------|---------|---------|
| **Supabase** | Auth, Realtime, RLS «household_id», Edge Functions для пушей, дешёвый старт | Нужно спроектировать таблицы/политики | **Выбор** |
| Firebase | Auth + FCM «из коробки», Firestore realtime | Сложнее строгие household-правила, vendor lock | Запасной, если упор только на FCM |
| Свой API | Полный контроль | Долго для семейного MVP | Не для v1 |

### Конфликты
- Один слот дня: **last-write-wins** по `updatedAt` (UTC) + показ «кто последний отметил».
- Два офлайн-изменения одного слота: побеждает более новый `updatedAt`; проигравшее можно кратко показать в UI («перезаписано: Мама»).
- Не мержить «среднее время» — это путает семью.

### Офлайн
1. Писать локально (IndexedDB / Capacitor Preferences; пока можно оставить `localStorage` + очередь синка).
2. Очередь мутаций `{ clientId, op, payload, ts }`.
3. При сети — push на сервер, Realtime подписка на `feedings` по `household_id`.
4. Тема и UI-настройки остаются **на устройстве**, не в семейном облаке.

### Этапы
- **v1:** аккаунт + создание/вход в household по коду; realtime-синк кормлений; роли owner/member.
- **v2:** несколько котов, история «кто кормил», экспорт, опциональный viewer-роль, веб-клиент с тем же API.

## 2. Уведомления

### Триггеры (локальные v1.7.1 + семейные позже)
Фразы собирает JS (те же падежи, что чип/приветствия); Android показывает готовый текст.

| # | Событие | Кому | Текст (пример) |
|---|---------|------|----------------|
| **C** | Кнопка «Покормить» | Это устройство | «Лию покормили только что» (вин.) |
| **B** | Нет кормления ~3.5 ч | Это устройство | «Пора покормить Лию!» (вин.) |
| **H** | Нет кормления >5 ч | Это устройство | «Лия совсем проголодалась!» (им. + род глагола) |
| **M** | Утро 06:15 | Это устройство | «Доброе утро! Не забудьте покормить Лию.» (вин.) |
| **A** | После записи кормления (семья, позже) | Всем в household, **кроме** автора | «Мама: коты покормлены в 08:15» |

### Тихие часы и интервал (сейчас / потом)
- **Сейчас (локально):** тихие часы **23:00–06:00** — срабатывания сдвигаются на **06:15**; напоминание **~3.5 ч**, «голод» **5 ч**.
- **Потом (настройки семьи/устройства):** `quietStart` / `quietEnd`, `reminderHours` в диапазоне **3–4 ч** (и опционально порог «голод»), `timezone` (IANA). Пока UI настройки интервала нет — константы в `FeedReminderScheduler` + JS `syncFeedNotifications`.
- Семейные серверные расчёты — в UTC; отображение — в TZ семьи.

### Android (APK = WebView + нативный AlarmManager) — v1.7
WebView **сам по себе** не даёт надёжных фоновых пушей. Реализация:

1. **Сделано:** JS-мост `MurCalendarAndroid.notifyJustFed(body)` / `scheduleFeedReminders(lastMs, reminder, hungry, morning)` → `FeedNotifier` + `FeedReminderScheduler` (`AlarmManager.setAndAllowWhileIdle`) + `FeedAlarmReceiver` (в т.ч. после BOOT). Падежи только в JS.
2. Канал `mur_feeding`; runtime `POST_NOTIFICATIONS` (API 33+).
3. **Ограничения WebView:** таймеры JS живут только пока процесс/вкладка живы; Doze/OEM могут откладывать exact alarms; без FCM нет доставки «с сервера» другим членам семьи.
4. **Дальше:** Capacitor/FCM + Supabase Edge для семейного A и страховочного B; интервал 3–4 ч — в Настройки.

### Web (план + хуки v1.7)
- **Сейчас:** при разрешении `Notification` — stub `webNotify` + `setTimeout` (только открытая вкладка); запрос permission при старте.
- **Позже (v2):** Web Push + VAPID + SW; те же тексты C/B/H/M; quiet hours на клиенте до появления сервера.

### Антиспам
- A: не чаще 1 раза на одно событие кормления; не слать автору.
- B: не чаще 1 раза за окно reminder; сброс таймера при любом новом кормлении в household.
- Дедуп по `feeding.id` / `clientId`.

## 3. Миграция с HTML-стаба + localStorage APK

### Что есть сейчас
- UI: месяц, 4 слота/день, темы, приветствия.
- Хранение: `mur-calendar-times` = `{ "YYYY-MM-DD": ["HH:MM", ...] }`, тема в `mur-calendar-theme`.
- APK: нативный WebView + `assets/index.html`, package `com.murcalendar.feeding`, без облака.

### Путь без ломки UX
| Шаг | Действие |
|-----|----------|
| **0** | Зафиксировать текущую схему ключей как «legacy local». |
| **1** | Слой `storage`: читать/писать через адаптер Local → позже Remote. UI не трогать по смыслу. |
| **2** | При первом логине в household: импорт `mur-calendar-times` → записи feedings (`fedBy` = текущий user или «импорт»). Тема остаётся локальной. |
| **3** | После успешного синка — флаг `migratedAt`; local остаётся кэшем/офлайн-буфером. |
| **4** | Заменить WebView-обёртку на Capacitor (тот же HTML/JS или лёгкий бандл), package можно сохранить. |
| **5** | Подключить Auth UI (вход / создать семью / код приглашения) поверх календаря. |
| **6** | Local notifications (B) → затем FCM (A + серверный B). |

### Совместимость
- Старый debug APK без аккаунта продолжает работать офлайн как сейчас.
- Новый билд: офлайн-режим без входа = прежнее поведение; вход включает семейный синк.
- Конфликт «два телефона с разными localStorage до первого синка»: при импорте **объединять по дням/слотам** (непустой слот побеждает; если оба непусты — больший `updatedAt` / при равенстве — ручной выбор редко нужен, LWW достаточно).

### Что не делать в v1
- Не писать отдельное нативное UI с нуля.
- Не тащить полный Firebase + полный Supabase сразу.
- Не публиковать в Play, пока нет release-подписи и политики аккаунтов/данных.

## 4. Web ↔ Android ↔ future iOS: почему облако (Supabase), а не порт WebView

Сейчас один HTML обслуживает и браузер, и Android WebView — это удобно для UI, но **не** является кросс-платформенной синхронизацией данных.

| Подход | Что даёт | Чего не даёт |
|--------|----------|--------------|
| **Порт того же WebView на iOS** (WKWebView + тот же `index.html`) | Одинаковый UI на третьей платформе | Общие кормления между маминым iPhone и папиным Android; общий аккаунт; пуши семье |
| **Облачный синк (Supabase)** поверх того же HTML/JS | Один источник правды для web + Android + iOS; Realtime; Auth/household; путь к пушам | Нужен бэкенд и слой storage (см. §1–3) |

**Вывод:** iOS-оболочка с WebView имеет смысл как **клиент** (как текущий APK), но семейная картина «отметил на одном устройстве — видно на всех» требует **облака**, а не копирования WebView. Supabase закрывает web + Android + будущий iOS одним API; локальный `localStorage` остаётся офлайн-кэшем. Порт WebView на iOS **без** синка лишь умножает острова данных.
